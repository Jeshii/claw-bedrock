## [Unreleased]

### Added

- **Bedrock auth is now configurable from the GUI, and changes take effect without a restart** — a "Bedrock Authentication" section below Manage Providers on the Providers page, holding the region, the AWS profile, and an opt-in static IAM key pair behind a collapsed advanced section. `PUT /api/settings/bedrock` persists, calls `token_refresher.configure()`, and re-mints a token in place; previously any of these meant editing the unit file and restarting the container. Values render with a source badge per field, so it stays visible when an environment variable is overriding what you typed.
- **`GET /api/health/litellm/liveliness`** — a liveness probe for the LiteLLM process. It is distinct from the existing `/api/health/litellm` on purpose; see the Fixed entry for why the two answer different questions. `scripts/smoke.sh` now asserts this one.
- **Encrypted settings storage** — `db.set_secret_setting` / `get_secret_setting` / `clear_secret_setting`, plus `encryption_utils.decrypt_data_strict`. `get_secret_setting` returns a **state** (`absent` / `ok` / `undecryptable`) rather than a bare value, so a secret restored under a different `ENCRYPTION_KEY` is distinguishable from one that was never set — `decrypt_data` returns its input unchanged on failure, which would otherwise hand raw Fernet ciphertext to boto3 as a credential (BUGS.md #8).
- **`BedrockTokenRefresher.configure()`** — re-resolves region, profile and credentials, drops the stale token, and forces a refresh with coalescing bypassed. A refresh triggered deliberately by a settings save must not be absorbed by a recent failed attempt.
- **`tests/test_bedrock_settings.py`** — 26 tests covering the settings endpoints, key-pair state matrix, encrypted round-trip, undecryptable-credential reporting, and the two health endpoints.
- **Two new diagnosis notes** in `AGENTS.md` under "Diagnosing the Running Container": LiteLLM's output goes to `${CONFIG_DIR}/litellm.log` and never to `podman logs`, and `/api/health/litellm` is not a liveness probe.

### Fixed

- **Static AWS credentials were inert on every install** — `token_refresher` always called `boto3.Session(profile_name=self._profile)`, and botocore sets `disable_env_vars` whenever a profile is passed explicitly (`credentials.py:95`), which removes the `EnvProvider` from the credential chain. `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` were therefore set but unread: the non-SSO path was broken for everyone. `_build_session()` now passes the credentials explicitly and omits `profile_name`, which is the only way to reach them (`boto3/session.py:81-82` only sets the profile config variable when `profile_name is not None`). A half-configured key pair still falls back to the profile rather than displacing it.
- **The Bedrock region field did nothing** — it was merged into `litellm_params["aws_region"]`, which LiteLLM's `GenericLiteLLMParams` does not declare and silently discards. The key it actually reads is `aws_region_name`, which is what is now written, sourced from the resolved global region. A per-provider region was also a lie regardless: there is one refresher, one `self._region` and one `BEDROCK_MANTLE_API_KEY`, so a second provider in another region would present a token minted for the first.
- **The Bedrock provider form collected configuration no runtime code read, and destroyed one of the fields on save** — `aws_access_key_env` / `aws_secret_key_env` named *environment variables* rather than holding credentials. Worse, `aws_secret_key_env` matched the `secret` substring, so the variable *name* was encrypted; `sanitize_provider_for_response` then nulled it, so the edit form always rendered blank, and saving wrote the blank back — opening a Bedrock provider, renaming it and saving silently popped the field. All three fields are now rejected by `PUT /api/providers/{name}` with a 400 naming the field, stripped on read and on write (so a restored backup cannot reintroduce them), and removed from stored records at startup by `db.migrate_dead_bedrock_fields()`.
- **`GET /api/health/litellm` reports `ok` whenever the probe does not raise**, whatever code LiteLLM returned. It also proxies `/health`, which is an *active* check — it makes a real call to every model in `model_list` unless `general_settings.background_health_checks` is set, which this config does not set. So the endpoint was coupled to provider auth: with Bedrock unauthenticated, nine models' worth of checks each attempt a token refresh and fail, and the set exceeds the probe's 5s budget, presenting as a proxy outage. It also passed **vacuously** with an empty `model_list`, which is how `scripts/smoke.sh` reported `litellm_status == 200` in CI while proving nothing about serving a request. `/api/health/litellm` is left on the active check deliberately — a red reading there means models genuinely cannot be served — and liveliness moved to the new endpoint, which the smoke test now uses.
- **The `env_credentials_shadowed_by_profile` warning is removed** — it was added to explain why env credentials were inert, and the fix above removes the cause. Keeping it would fire on a condition the same release repairs.
- **Stored secrets are reported as presence, never echoed** — the key pair follows the existing provider `api_key` convention (a boolean, no value, no masked prefix) rather than the LiteLLM master key's `key[:12] + "..." + key[-4:]` reveal. An AWS access key ID is half a credential; its prefix identifies the account and key vintage.
- **A settings save that persists but cannot mint a token no longer reports success** — `PUT /api/settings/bedrock` returns `saved` and `token_refreshed` separately, and the UI shows `Saved, but no token could be minted`. A wrong region or a bad key fails at token-mint time, not at validation.
- **A saved region that is not lowercase is corrected with a warning rather than rejected** — botocore can enumerate Bedrock regions offline, but only for the public partition, so validation would falsely reject GovCloud and regions AWS adds later. A wrong region fails loudly at mint time; a false rejection is worse.
- **`settings_resolver` held a module-level `db` reference** that went stale under the test suite's module reloading, so `db.get_setting()` raised `I/O operation on closed file` from the config-generation path. The import is now per-call.
- **`docs/BUGS.md` #10 claimed `bedrock_mantle` exposes no `/models` endpoint** — it does. Verified live: `/v1/models` returns 401 (wants a bearer), `/openai/v1/models` returns 404. The claim made model discovery look impossible. The 404 is the real constraint and is documented: the gpt-5.x, gpt-6-\*, gemma-4-\* and grok-4.x families are served on `/openai/v1`, so a fetched list will not contain them.

### Corrected documentation

- **`docs/ROADMAP.md` recorded three claims that host verification disproved**, each an inference from an absence that something structural guaranteed:
  - *"LiteLLM's own log had produced no `Uvicorn running on :4000` line, so it appears stuck or still initialising"* — `start_container.sh:56` redirects LiteLLM's output to `${CONFIG_DIR}/litellm.log`, so `podman logs` can never contain it. LiteLLM had been up throughout.
  - *CI's `litellm_status == 200` closing the `linux/amd64` gap* — the CI container has no models, so the assertion passed vacuously. The honest claim is narrower: the amd64 image boots and the management UI serves. Whether LiteLLM serves *requests* on amd64 is still unproven.
  - *Step 1's host verification pending* — it was run, and passed vacuously: `auth_error` was `null` in both responses, so the diff would have been identical against the old read-and-clear code. Step 1 rests on its unit tests and nothing else. A green double-diff is not evidence unless there was something to differ on.
- **`docs/BUGS.md` gained #11 and #12** for the two traps above, and `AGENTS.md` gained the matching "Diagnosing the Running Container" section.

- **The container shipped without `settings_resolver.py` and could not boot** — `.github/Containerfile` copied each Python module with its own `COPY` line, and `settings_resolver.py` was added to `src/` without a matching line. The image built clean, every test passed, and the app died at import: `ModuleNotFoundError: No module named 'settings_resolver'`. Because `start_container.sh` ends in `wait ${MGMT_PID}`, the management process exiting took the container down with it, so port 8282 stopped serving entirely and the unit sat in a `Restart=on-failure` loop. Now `COPY src/*.py .`, so a module cannot be added without being shipped. This is the second time the enumerated list lost a module (`8a9ff62` recovered `encryption_utils.py` and `password_utils.py` the same way), which is why the list is gone rather than extended.
- **First boot with no mounted config volume killed the container** — `init_configs()` copies `/app/token_refresher.py` to `$CONFIG_DIR/token_refresher.py`, but the image sets `CONFIG_DIR=/app`, so an unmounted boot ran `cp` with identical source and destination. `cp` exits 1 with "are the same file" and `set -euo pipefail` turned that into a dead container before either process started. Deployments never hit it because `CONFIG_DIR` points at a mounted volume. The copy is now skipped when source and destination are the same file.
- **`GET /api/health/litellm` reported `ok` when LiteLLM was unhealthy** — the handler returns `status: ok` whenever the probe does not *raise*, so a 404 or 500 from the proxy still read as healthy. `scripts/smoke.sh` asserts `litellm_status == 200` as well, which is the assertion that means something.
- **`docs/ROADMAP.md` documented the wrong build command** — `podman build -f Containerfile .` names a path that does not exist; the file is `.github/Containerfile`. The root `Dockerfile` is a separate thin layer that builds on the published image, not a copy of it.
- **The image build had never actually run in CI, so the fix above could not ship** — the build job failed at setup in 1m0s on every run since `a834ee8`, publishing nothing, while the roadmap reported the incident verified. `a834ee8` added `cache-to: type=gha,mode=max` to a workflow that never called `docker/setup-buildx-action`, so the runner used its implicit default builder — the `docker` driver, which supports gha cache import but not export: `Cache export is not supported for the docker driver`. Two more bugs sat behind it: `IMAGE: ${{ steps.meta.outputs.tags }}` bound a multi-line block (`develop` + `sha-<short>`) into one env var, so the smoke test would have passed two tag names to `docker build -t`; and the step ran with no `SKIP_BUILD`, so it would have rebuilt from scratch instead of booting the artifact about to be pushed, defeating the build → smoke → push arrangement. The smoke step now gets a single local-only tag, is never pushed, and boots the loaded image, with `CONTAINER_ENGINE: docker` pinned because `smoke.sh` prefers podman and podman's store is separate from Docker's. The gha cache was removed rather than repaired: it buys ~85s of a 90s build by pushing ~950 MB up and back down per push into a store that expires silently after 7 days, and it had already cost one broken build plus a false verification claim. The `docker-container` driver would restore it in four lines if the build gets painful.
- **An unmounted first boot could report a false pass** — a diff of two empty files is empty, so a health check run before the port was serving looks identical to a passing one. The container binds 8282 only after the config merge completes, and here that took ~40s past restart.

- **Auth errors were consumed by status polling before anyone could see them** — `get_auth_error()` was read-and-clear and the management app called it from inside `GET /api/auth/status`, while the auth page re-polls every second during a login flow. A login error could therefore be consumed by a poll in under a second and never displayed. Replaced with `peek_auth_error()`, which does not clear; the error is now cleared where it genuinely stops being true, on a successful token refresh and at the start of a new login attempt. Read-and-clear had been doubling as the de facto reset, since nothing else cleared `_auth_error` — peeking alone would have left a stale error on the page indefinitely. The proxy's `/auth/status` and the management endpoint now share one `auth_status_payload()`; they previously built the same response by hand and disagreed, with the proxy reading `_auth_error` directly and only the proxy reporting the profile.
- **Router Settings saved strategy values LiteLLM does not accept** — the Groups page dropdown wrote `latency-based`, `usage-based` and `cost-based`, but LiteLLM's Router takes `latency-based-routing`, `usage-based-routing` and `cost-based-routing`. Unrecognized strategies are ignored at proxy startup, so a saved setting looked applied while routing silently stayed on the default. New `db.ROUTING_STRATEGIES` / `db.normalize_routing_strategy()` are the single source of truth; `get_router_settings()` maps the old short forms forward so existing installs heal with no migration, and `POST /api/settings/router` now rejects an unknown strategy with a 400 listing the valid values instead of storing a value that does nothing.
- **UI bookkeeping leaked into the generated LiteLLM config** — `get_models_for_litellm()` copied every stored model field into each `model_list` entry, so `provider`, `tags` and `reasoning_effort` were written to `config.yaml`. Now dropped via `db.UI_ONLY_MODEL_FIELDS`. A denylist rather than an allowlist, because records migrated from an older `config.local.yaml` can carry genuine top-level LiteLLM keys (`rpm`, `tpm`) that an allowlist would silently discard.
- **Models from custom providers now include `api_base`/`api_key` in `litellm_params`** — `addGenericModel()` in `models.js` looks up the provider from `window._allProviders` and propagates its endpoint and credentials into the model config. Also switched the model prefix from `providerName/modelId` to `openai/modelId` (the correct prefix for OpenAI-compatible endpoints).
- **Config pushed to running LiteLLM after model CRUD** — `_reload_litellm_config()` is now called after `merge_configs()` in `add_model()`, `delete_model()`, `rename_model()`, and `update_model()` in `management_app.py`. Previously the config file was written but the running process was never notified.
- **Playground dropdown refreshes when reload modal blocks navigation** — `loadPlayground()` called immediately in `navigation.js` before the `needsReload` guard returns early, so the model list is populated from TinyDB even while the reload decision is pending.
- **Playground model dropdown retries and manual refresh** — added retry buttons to all error/empty states in `loadPlayground()` (`playground.js`), and a refresh `↻` button next to the model select (`page_playground.html`). Navigation now calls `loadPlayground()` on every Playground tab activation (`navigation.js`).

### Added

- **`scripts/smoke.sh` boots the image and asserts it serves** — run by `build-container.yml` between the build and the push, so a broken image is never published. `docker build` never executes `ENTRYPOINT`, which is how an image that cannot import its own modules reported a healthy build and reached a running service. Two assertions: `GET /api/version` returns the baked `/app/VERSION` (proves the app imported and its templates/static loaded) and `GET /api/health/litellm` returns `status: ok` *with* `litellm_status: 200`. On failure it dumps container logs and `ls /app`, which names a missing module outright. Also runnable locally, honouring `$CONTAINER_ENGINE`, with `SKIP_BUILD=1` to test an existing image. The smoke step runs with `SKIP_BUILD=1` in CI, so it boots the artifact the push step publishes rather than rebuilding a second one.
- **`tests/test_containerfile.py` asserts every `src/*.py` is copied** — the cheap static half of the same guarantee. Runs in the `test` job in seconds, names the missing file in the failure message, and still holds if the smoke test is ever muted for flakiness. Also asserts `templates`, `static` and `start_container.sh` are copied, since a missing asset directory does not fail at import but on the first request that touches it.
- **Bedrock auth status reports what is actually in effect** — `GET /api/auth/status` gained a `bedrock` block with the region and profile in use, which layer of the precedence chain each came from, token freshness, and whether static AWS keys are present. The Auth page renders it with a source badge per value. All five keys the auth UI depends on are unchanged. Values are read from the token refresher rather than the resolver, because those are what the token was actually minted against — the resolver only classifies provenance, so a disagreement is visible rather than silently wrong. A `env_credentials_shadowed_by_profile` warning fires when `AWS_ACCESS_KEY_ID` or `AWS_SECRET_ACCESS_KEY` are set alongside an explicit `AWS_PROFILE`: botocore drops the env-var credential provider whenever a profile is passed (`credentials.py:95`), so those variables are set but inert. The warning reports presence only, never values.
- **Settings precedence resolver** — new `src/settings_resolver.py` resolves any setting that has both an env var and a stored form, walking flag → env → config → default and reporting the winner plus the lower layers it shadowed. This is the mechanism behind the GUI-yields-to-environment principle: an expert who sets an env var is never silently overridden by a form they filled in months ago, and the GUI says which variable won. `default` is excluded from `shadowed` because it is a fallback rather than a choice anyone made. Config keys are namespaced (`bedrock_region`) rather than reusing env var names, since config import writes keys verbatim from a restored backup.
- **Cost awareness**
  - Models can record `input_cost` / `output_cost`, entered and stored as **dollars per 1M tokens** — the unit Bedrock and OpenRouter quote — with editable inputs in the model detail section (`models.js`)
  - `db._apply_model_costs()` converts to per-token and writes `litellm_params.input_cost_per_token` / `output_cost_per_token`, which is what LiteLLM's `cost-based-routing` actually reads, and mirrors the values into `model_info` for spend reporting without clobbering existing keys such as `supports_tool_calling`
  - The roadmap spec only called for `model_info`, which the router never consults. Its fallback cost-map lookup is a direct dict lookup that misses provider-prefixed names such as `bedrock_mantle/…` and `openai/…`, defaulting to $5/$5 ([BerriAI/litellm#35787](https://github.com/BerriAI/litellm/issues/35787)) — so an unpriced model reads as one of the most expensive in its group and is never picked, rather than as "unknown"
  - Groups page shows a per-member price chip, a "cheapest" chip on the group header, and a **no cost** warning on unpriced members while cost-based routing is active
  - `PATCH /api/models` accepts both fields; blank clears the key (via the new `db.unset_model_field()`, since TinyDB's `update()` merges and cannot delete), and non-numeric, negative, NaN/Inf and boolean values are rejected 400 before anything is written. `0.0` stays a real price rather than reading as blank
  - **OpenRouter prices are auto-filled** when a model is picked in the add form — the catalog response already carried a `pricing` block, so this was pulled forward from Polish
  - `GET /api/model-groups` reports the active `routing_strategy` so the dashboard knows when costs matter
  - `tests/test_model_costs.py` — 31 tests covering per-token conversion, free models, `model_info` merging, config cleanliness, PATCH validation and clearing, and the groups payload
  - `tests/test_router_settings.py` — 17 tests covering strategy normalization, round-tripping every literal, rejection, and clearing

- **Groups dashboard**
  - New `GET /api/model-groups` endpoint aggregating models by `model_group`, with provider display info attached to each member
  - New Groups page (`templates/partials/page_groups.html`, `src/static/js/groups.js`) listing every group, its member count, and expandable members with provider badges and context length
  - Per-member status chips derived from config only: `Ready`, `Check config`, `Not in config`. No live probing — status reflects what is actually written to `config.yaml`
  - Group header reports `active_member_count` vs `member_count`, surfacing members silently dropped from the generated config by `db._merge_provider_defaults` (e.g. a dangling provider reference)
  - Clicking a member jumps to the Models page with that model expanded
  - Ungrouped-model summary with a shortcut to the Models page
  - `tests/test_model_groups.py` — 11 tests covering aggregation, sorting, status levels, `active_member_count`, and secret redaction
- **Model groups with auto-failover**
  - New optional `model_group` field on models — when set, multiple models sharing a group form a LiteLLM failover group
  - `get_models_for_litellm()` in `db.py` now transforms `model_group` into LiteLLM's `model_name`, with prefix applied if configured
  - `PATCH /api/models/{name}` accepts `model_group` for per-model assignment
  - `GET/POST /api/settings/router` — expose `routing_strategy`, `allowed_fails`, and `num_retries`
  - Group badge displayed in model rows in the UI
  - Inline group-name input in the model detail section
  - New Router Settings section in the Models page (strategy, fails, retries)
  - Backward compatible — models without `model_group` behave identically to before

### Added

- **Group management on the Groups page** — the dashboard was read-only, so an unwanted or typo'd group could only be cleared by expanding every member on the Models page and emptying the input one at a time.
  - `POST /api/model-groups/rename` `{from, to}` and `POST /api/model-groups/unassign` `{name}`. Both apply every member in one batch and issue a single config push, so a mid-way failure cannot leave a group split across two names
  - Per-group **Rename** and **Unassign** buttons, plus an **add member** dropdown fed by the models currently in no group
  - Rename is gated behind a confirm that spells out the consequence: a group name *is* the model name clients call, so the old name stops working
  - Rename deliberately refuses to merge onto an existing group (409) rather than silently repointing the losing name's clients
- **`ungrouped_models` on `GET /api/model-groups`** — the ungrouped model names, not just the count, so the add-member dropdown can be built without a second request
- **Group-name suggestions on the Models page** — the Group input is now a `list=` datalist fed from the same response, so a typo cannot silently invent a near-duplicate group

### Fixed

- **Group names are validated.** A name becomes the public `model_name` (`db.get_models_for_litellm`, optionally prefixed `claw-bedrock/`) but nothing checked it, so a name containing whitespace produced a model name no client could request. An allowlist of letters, numbers, dots, dashes and underscores; empty, over-64-char and non-matching names are rejected with 400, and surrounding whitespace is trimmed so a trailing space cannot create a near-duplicate.
- **`.rename-btn` was 2.33:1 in dark mode.** It paired `var(--neutral)` with `var(--text-inverse)`, but unlike `--danger`/`--success` (which lighten for dark mode) `--neutral` gets *darker*, so dark mode painted dark text on a dark fill. Added `--text-on-neutral`.
- **`.rename-btn.confirming` was 3.13:1 in light mode** — white on mid-green. Added `--text-on-success`. Both buttons are used on the Models page too, so this fixes them there as well.

### Changed

- **Context length formatting** — `formatContextLength` divided by 1024/1048576 while model catalogs report decimal units, and never rounded, so a 1,000,000-token model rendered as `976.5625k ctx` instead of `1M ctx`. Now divides by 1000/1e6 and suppresses trailing zeros (128k stays 128k, not 125k).
- **Model render path no longer assumes `litellm_params` exists.** `POST /api/models` does no validation, so a model without it is creatable, and the unguarded dereference threw mid-map and blanked the whole Models page.
- **Router Settings moved to the Groups page.** `routing_strategy`, `allowed_fails` and `num_retries` are failover behavior for model groups, but the controls lived on the Models page — the one place you cannot see a group. Pure relocation; the API is unchanged.
- **Rebuilt light/dark mode on a design-token layer** — `management.css` had **zero** CSS custom properties; all 66 colours were hardcoded and 106 one-off `.dark X {}` rules patched individual selectors. 26 of those 66 colours existed *only* inside `.dark` rules, i.e. dark mode had a deliberately designed palette while light mode inherited browser defaults.
  - 60 semantic tokens (surfaces, interactive states, borders, text, accent, status, alpha overlays, shadows) declared once in `:root` with `light-dark()` for their dark value, matching the pattern `login.html` already used
  - `color-scheme: light` on `:root` / `color-scheme: dark` on `.dark` makes `light-dark()` resolve and themes native scrollbars and form controls, which the app never themed
  - 105 `.dark` override rules deleted, folding into the token block. One survives — `.dark #reload-litellm-btn.needs-reload { animation }` — because an animation is not a token
  - **Fixed: invisible hover states in light mode.** Nine hover rules used `#f8f9fa` on a white page — a contrast ratio of **1.05:1**, effectively invisible. Hover tokens are now 1.24:1 (light) and 1.38:1 (dark), matching dark's perceptual step
  - **Fixed: `.section` had no light background** (transparent, relying on a white body) while dark got `#2a2a2a`; both now use `--bg-surface`
  - **Fixed: `input`/`select` and bare `pre` were styled only in dark mode.** `.dark select` and `.dark pre` were the sole source of their background, so deleting those rules would have left white-on-white inputs and log viewers. Both now carry explicit token-backed base styles
  - **Fixed: Playground surfaces had no dark styling at all.** `.playground-toolbar`, `.playground-input-area` and `.playground-messages` kept `#f8f9fa`/`#fefefe` with `#ddd` borders in dark mode — the Playground shipped after the dark-mode pass and was never covered. The token layer fixes this automatically
  - Dark values are carried over from the previous stylesheet wherever dark mode already had an intentional value, so its overall appearance is preserved. A computed-style diff of the whole rendered page, old stylesheet vs new, found the exceptions — see below
  - Requires `light-dark()` support (Chrome 123+, Safari 17.5+, Firefox 120+) — the repo already depended on it via `login.html`
- **Contrast regressions the token layer introduced, found by diffing computed styles across the whole rendered page (old stylesheet vs new) and measuring WCAG contrast on every text element in both themes.** Dark mode: 3 → 2 failing elements. Light mode: 11 → 4.
  - `.btn-primary`, `.nav a.active`, `.message-user` and `#sysprompt-toggle.active` paired `--accent-fill` with `--text-inverse`. `--accent-fill` is a mid/dark blue in *both* schemes, so dark mode painted `#1a1a1a` on `#0056b3` — **2.47:1**. Added `--text-on-accent`
  - White on the old light `--accent-fill` `#007bff` was only 3.80:1, so the light value is now `#0069d9` (5.22:1)
  - `--warn-on-warn` was `#ffe082` in dark mode on `--warn` `#ffc107` — **1.26:1**. `--warn` is identical in both schemes, so the text is now `#333` in both
  - `.rename-btn` paired `--neutral` with `--text-inverse`, but unlike `--danger`/`--success` (which lighten for dark mode) `--neutral` *darkens*, giving **2.33:1**. Added `--text-on-neutral`
  - `.rename-btn.confirming` was white on mid-green, **3.13:1** in light. Added `--text-on-success`. Both buttons also appear on the Models page
  - `.sidebar-backdrop` (mobile hamburger) was given opaque `--bg-raised` instead of the `--bg-scrim` token, so it would have covered the page instead of dimming it
  - `.section` lost its dark `#2a2a2a` surface when the `.dark .section` override was folded into the token layer; now `--bg-surface` in both schemes (light is `#ffffff`, identical to the body, so light is unchanged)
  - `#reload-litellm-btn.needs-reload` lost its dark `#1a3050` tint, and `dialog` shifted from `#2a2a2a` to `#1a1a1a`; both restored
- **Converted the remaining inline colours to tokens** — the token migration only caught colours a single-line search matched, missing multi-line `style` attributes: 12 dialog borders in the Logs page, 4 more `#ccc`/`#ddd` borders, the key-reveal code background, Backup's empty-state text, the Tags Cancel button, three status colours set from JS, the auto-refresh toggle, Backup's drag-over border, and the provider swatch border. `--swatch-border` was also defined as `light-dark(rgba(0,0,0,.15), rgba(0,0,0,.15))` — identical branches, i.e. a black border invisible on a dark swatch. Deliberately left alone: the ANSI terminal palette, the user-chosen tag colours, and provider swatch colours, which are data rather than theme.
- **`navigation.js` page dispatch consolidated** — the page-activation and loader-dispatch block was duplicated between `showPage()` and `dismissReloadWarning()`; it is now a single `activatePage(pageId)` helper.
