# Build Dependencies - Skill

## Python version

The runtime Python version is defined in one place only: the `FROM` line of
`.github/Containerfile` (currently `python:3.14-slim`). `ruff.toml`'s
`target-version` must match it.

`pip-compile` **must be run in a virtualenv built on that same Python
version**, because it resolves against the running interpreter's available
wheels and `requires-python` metadata. A lock generated on a different version
can be un-installable on the target.

```bash
python3.14 -m venv .venv
.venv/bin/pip install pip-tools
.venv/bin/pip-compile --output-file=requirements.lock requirements.txt
```

The header of `requirements.lock` records the version used — check it says
`Python 3.14` after every regeneration.

### Ceiling: litellm blocks Python 3.15

`litellm` declares `requires-python = ">=3.10,<3.15"`, so **3.14 is the
newest Python this project can run**, even though newer CPython releases
exist. The `litellm[proxy]>=1.93.0` floor in `requirements.txt` exists for
the same reason: 1.93.0 is the first release that lifted its ceiling from
`<3.14` to `<3.15`. Raising that floor is what unblocks a new Python; check
litellm's `requires_python` before attempting a bump.

Note that `litellm[proxy]` also pins `fastapi`, `starlette`, `aiohttp`,
`uvloop`, and `orjson` transitively, so a litellm bump can force a FastAPI
major move. Run the test suite before committing.

## Regenerating requirements.lock

The lock file is auto-generated by `pip-compile` (from `pip-tools`). **Never
edit it manually** — always regenerate it after changing `requirements.txt`.

### Prerequisites

```bash
# In a venv on the Containerfile's Python version (see "Python version" above)
pip install pip-tools
```

### Regenerate

```bash
pip-compile --output-file=requirements.lock requirements.txt
```

This resolves the full dependency tree and pins a single, consistent version of
every package. If pip-compile fails, the conflict is in `requirements.txt` —
loosen or remove version pins there, then re-run.

### Common Failure: ResolutionImpossible From Stale Pins

pip-compile reads the existing `requirements.lock` and treats those pins as
constraints, preferring them over newer releases. So after raising a floor in
`requirements.txt` (e.g. `litellm[proxy]>=1.93.0`), it can fail because a
package the new version needs is still pinned below that floor:

```
ERROR: Cannot install ... because these package versions have conflicting dependencies.
Discarding fastapi==0.124.4 (from -r requirements.lock (line 95)) to proceed the resolution
```

pip-compile auto-discards pins it can prove are in the way, but a *transitive*
floor often needs help. Pass the blocked packages explicitly:

```bash
pip-compile --upgrade-package aiohttp --upgrade-package uvloop \
  --output-file=requirements.lock requirements.txt
```

If several conflict in turn, fall back to a full refresh with `--upgrade` and
review the resulting diff. Back the file up first:

```bash
cp requirements.lock .scratch/requirements.lock.bak
```

### Common Failure: Duplicate Package Versions

If the Docker build fails with `ResolutionImpossible` mentioning two versions
of the same package (e.g. `cryptography==47.0.0` and `cryptography==48.0.0`),
the lock file was edited manually or merged incorrectly. Fix by regenerating:

```bash
pip-compile --output-file=requirements.lock requirements.txt
```

### Workflow

1. Edit `requirements.txt` (loose pins, e.g. `cryptography>=46`)
2. Run `pip-compile --output-file=requirements.lock requirements.txt`
3. Verify the lock file has no duplicate packages:
   ```bash
   grep "^cryptography==" requirements.lock | wc -l  # should be 1
   ```
4. Run lint checks per AGENTS.md
5. Commit both `requirements.txt` and `requirements.lock`
